# PlayMint — AI Implementation Status

PlayMint turns a text prompt into a playable browser game (**Runner** or **Action
Quest** platformer) with all visual assets generated by AI at play time. This document
is the current, complete picture: how to use it, how the generation pipeline works,
what it costs, and what its limits are. A dated change history is at the bottom.

---

## 1. Setup & use

### Run it

```bash
npm install
npm run dev        # → http://localhost:5173  (the only command needed)
```

Or use the deployed build at **https://playmintai.vercel.app** — no local setup.

### Add your Gemini API key — in the app (recommended)

The app works without any key (see "Free engine" below), but a Gemini key unlocks the
fast path, real art direction, vision quality control, and the animated player.

1. On the start screen, look at the **top-right corner**.
2. Set the **Provider selector** to **Gemini**.
3. A field labeled **"Insert Gemini API key:"** appears — paste your key, press
   **Save**. The field collapses to a **✓** tick: the key is active. It is stored in
   your browser only (localStorage), survives reloads, and you can click the ✓
   anytime to change it.
4. Get a key at https://aistudio.google.com/apikey. The key's Google Cloud project
   must have **billing enabled** — since December 2025 Google's free tier serves
   0 images/minute on every image model, so an unbilled key cannot generate images
   at all.

Alternative for local development: put `VITE_GEMINI_API_KEY=your-key` in `.env`
(template in `.env.example`) before starting the dev server. The UI then shows the ✓
automatically. The in-app method is preferred: no restart, works on the deployed
site, and each tester can use their own key.

### Free engine (no key)

Without a key — or with the provider selector set to **Pollinations** — the app uses
the free, keyless Pollinations engine. Everything still works; the differences:
generation takes ~3–8 minutes (Pollinations only allows about one image at a time —
an upstream limit, not a bug), there is no vision quality control, and the player is
usually a static sprite with procedural motion instead of a full run cycle. The
progress bar ticks continuously the whole time so a slow run is visibly alive.

### Generate and play

1. Type a prompt on the start screen. Prompts that DON'T match the built-in themes
   show off the real art direction best:
   - Runner: `city runner in an underground bunker fallout 76 inspired`
   - Action Quest: `ancient jungle temple quest with stone golem enemies, vine
     covered ruins and glowing spike traps` (select the **Action Quest** bubble)
2. (Optional) Pick a mode bubble — **Runner** or **Action Quest**; unselected lets
   the prompt decide. **Generate** starts the build; the compiler-style terminal
   shows asset-by-asset progress. **Quick Start** launches a random preset instead.
3. Controls — Runner: SPACE to jump. Action Quest: WASD/arrows to move, SPACE jump,
   E melee, F shoot. Mobile devices get on-screen touch controls.
4. In game, the **Menu** (top-right) opens the Creator Panel:
   - Live sliders for physics/difficulty — applied instantly.
   - The **"Regenerate with Prompt"** box is an AI live editor. Plain-language
     requests are classified automatically: variable tweaks ("make it faster",
     "double the enemies") apply instantly with a ✓ summary; art changes ("make the
     enemy a robot", "change the foreground") redraw ONLY the named elements and
     keep everything else including your slider tweaks; full re-themes ("turn this
     into a lava world") re-skin all artwork but keep the mode and tuning. Asking to
     switch game modes gets a polite explanation instead (by design: new mode = new
     game).
   - Export/import config and share links.

### Switching providers (for testing)

The top-right **Provider selector** is authoritative:

- **Gemini** → Gemini-primary. Each asset still falls back to Pollinations
  automatically if Gemini errors or runs out of quota.
- **Pollinations** → free path forced; ALL Gemini calls are off (images, art
  direction, vision QA, live-editor AI) so the free experience can be evaluated in
  isolation.
- Never touched → `.env`'s `VITE_FORCE_POLLINATIONS=1` (if present) selects the free
  path; otherwise Gemini when a key exists.

No-restart console alternative: `localStorage.PM_FORCE_POLLINATIONS='1'` (or `'0'`)
and reload.

## 2. How it works — the pipeline in seven steps

Every generated game runs the same pipeline (`src/game/assetPipeline/`). In order:

**Step 1 — Prompt → game config (local, instant).** Keyword parsing picks the mode,
physics, difficulty, level layout, and title from the prompt text. No API call; this
is why the game skeleton always exists even if all image generation fails.

**Step 2 — Art direction.** One Gemini text call turns the prompt into a style guide
plus a subject description for every asset ("bunker-themed rusted metal floor…"),
including a reserved accent color palette for player/enemy/hazards so gameplay
elements always stand out from the scenery. Without a key, a local prompt-first
designer builds the subjects from the prompt text itself (a matched theme contributes
only palette and mood — never replaces the prompt).

**Step 3 — Image generation, per asset.** Up to 9 assets per game: far/mid/near
background layers, floor, platform, player, enemy, obstacle, and (Action Quest only)
projectile. Models are tiered by job: scenery uses `gemini-3.1-flash-lite-image`
(cheap), the player and their animation sheet use `gemini-3.1-flash-image` (the
consistency workhorse, sheet rendered at 2K and supersampled down). If a key can't
serve the 3.x models, the code detects it once and silently falls back to the older
model. Each asset walks a retry ladder — Gemini (2 attempts) → Pollinations (2
attempts) → built-in theme artwork — so **generation never dead-ends**: the worst
case is a playable game on stock art with a terminal line saying so.

**Step 4 — Background removal (keying).** No image model outputs transparency, so
sprites are requested on a **chroma-key green screen** (exact #00FF00; magenta
automatically for green-looking subjects so a slime monster doesn't vanish; the free
path stays on white). A border-connected flood fill then removes the backdrop —
robust to any color, and it protects white details INSIDE sprites (eyes, teeth,
visors). Safety fallbacks key whatever backdrop color was actually detected.

**Step 5 — Edge cleanup.** The standard sprite-pipeline chain: erode the anti-aliased
fringe → suppress leftover green/magenta spill at the edges → stamp a dark outline
under characters and hazards (the classic pixel-art readability guarantee) → bleed
edge colors outward so GPU texture filtering can't paint halos.

**Step 6 — Quality gates and the visual double-check.** Deterministic checks run on
every asset with no API cost: leftover-backdrop measurement with an automatic re-key,
transparency gates on the parallax layers ("did it keep a painted sky?"), geometry
checks. On top of that, a cheap Gemini vision call reviews the player and enemy —
wrong facing is mirrored client-side, dirty backgrounds get a re-key then at most one
regeneration. QA is **corrective, never fatal**: any QA failure means "proceed
unverified", never a dead run. Optional layers that can't pass are dropped rather
than shipped broken.

**Step 7 — Player animation assembly.** The static player is generated FIRST and
fully finished; then the animation sheet is requested as an image **edit** of that
exact character ("redraw THIS character in 9 poses" — a 3×3 grid: 8-phase run cycle
plus a jump pose). The sheet is cut at the cell boundaries the model actually drew,
each cell is background-keyed individually, and every frame is scored: geometry
(empty/undersized), identity (color-histogram vs. the other frames), and continuity
(silhouette overlap with neighbors — catches both "different character in frame 4"
and duplicated frames). Then, in escalating order of cost:

- up to 2 bad frames are simply **culled** (the remaining 6–7 frame cycle ships,
  playback speed auto-adjusts);
- 1–4 flagged frames trigger **repair** — just those frames are redrawn individually
  with the character reference attached;
- a failed sheet gets one **premium rescue** attempt on `gemini-3-pro-image`;
- then **per-frame escalation** — every pose drawn as its own reference edit (≤10
  calls);
- and if everything fails, the already-finished static player ships with a subtle
  procedural run bob, so the character never looks frozen.

Surviving frames are aligned (center of mass, shared ground baseline, height
normalization), locked to the static character's color palette (kills frame-to-frame
color flicker), and reviewed by the vision model as a **numbered filmstrip** — it
answers "same character in every frame? do the legs alternate? which frame numbers
are broken?" and flagged frames are culled before anything ships. The free path asks
for a simpler 2×2 four-frame stride instead (larger cells suit the free model);
choppier, but it animates.

## 3. Providers, speed & cost (current)

| Path | Models | Speed | Cost per game |
|---|---|---|---|
| **Gemini** (key required, billed) | `gemini-3.1-flash-lite-image` (scenery) · `gemini-3.1-flash-image` (player + sheet, 2K) · `gemini-3-pro-image` (rescue only) · `gemini-flash-latest` (art direction + vision QA) | ~15–30 s | ≈ $0.45 typical; worst case ≈ $1.10 when every rescue rung fires |
| **Pollinations** (free, keyless) | `sana` (only model on the free tier) | ~3–8 min (upstream one-at-a-time limit) | free |

`window.__GAME_LIVE_CONFIG.assetMeta` records, per asset, which provider AND which
model actually produced it, attempt counts, QA verdicts, and animation frame data.

### What to look for when testing the Gemini path

- Terminal: `Ready: player via gemini (4/8)`-style lines per asset, plus the new
  quality-loop lines when they fire: `Repairing N bad frame(s) individually...`,
  `trying the premium image model...`, `Dropped N inconsistent frame(s) from the run
  cycle`, `drawing 9 poses individually via Gemini...`.
- DevTools: `assetMeta.slots.player.model` should read `gemini-3.1-flash-image`
  (one console warning + `gemini-2.5-flash-image` instead means your key/region
  doesn't serve 3.x yet — the fallback is automatic and harmless).
- The player runs an 8-frame cycle with alternating legs (fewer frames = culling
  fired; `perFrame: true` in the meta = escalation fired); sprites have dark
  outlines, no white edges or colored boxes; three background layers scroll at
  different speeds; in Action Quest, **F** fires the generated projectile and
  platform art lines up with where you land.

## 4. Known limitations

- **Enemy is static.** The whole animation machinery (sheet, scoring, repair,
  escalation) is built for reuse; applying it to the enemy is designed but deferred.
- **Free-path animation is a lottery.** The free model rarely draws a usable sheet;
  gates reject bad ones, so free-path players are usually static with procedural
  motion. By design — a bad animation is worse than none.
- **Gemini quota sensitivity.** Heavy testing can hit per-minute/per-day limits; the
  run then silently degrades to the free path (check the provider summary line if
  results look worse than expected).
- **Occasional keying edge cases.** Enclosed background pockets between a character's
  limbs can survive (deliberate trade-off protecting white details), and rare
  gradient backdrops can leave minor artifacts despite the self-checks.
- **Client-side API key.** The key is visible to the browser — accepted trade-off
  for demos/prototypes; a production deployment should proxy Gemini calls
  server-side.
- **Non-Vercel production hosts** need a `/api/pollinations/*` →
  `https://image.pollinations.ai` rewrite rule for the free path (the dev server and
  the included `vercel.json` provide it; without it only the Gemini path works).
- **Resolution consistency** across assets is improved by the 2K sheet supersampling
  but not yet uniform — some assets can still read sharper than others in one game.

## 5. Change history

**2026-08-05 — Animation quality overhaul, phase 2.** Upgraded to the Gemini 3.x
image model tiers (with automatic fallback for keys without access); sheets render at
2K and are supersampled down; sprites moved to chroma-key green/magenta screens with
edge despill; added frame repair (redraw only the bad frames), the
`gemini-3-pro-image` rescue attempt, the numbered-filmstrip vision review with
per-frame verdicts, silhouette-overlap continuity metrics, palette locking
(color-flicker fix), center-of-mass alignment, and content-aware sheet slicing.
Same-day fix: small sprites (projectile) tripped a keying safety guard whose fallback
only understood white backdrops → shipped as a solid green box; the guard now fires
only on near-total wipes and keys the detected backdrop color.

**2026-07-31 — Animation continuity overhaul.** Per-frame alignment to a shared
baseline (the main "teleporting frames" fix), per-frame background re-keying
(flicker fix), culling of up to 2 bad frames instead of rejecting the sheet,
per-frame Gemini escalation (≤10 reference edits), and the free-path 2×2 four-frame
cycle.

**2026-07-31 — Free-path prompt fidelity.** The user's prompt now always drives asset
subjects on the free path (matched themes contribute palette/mood only), fixing
"on-theme but off-prompt" assets. A free AI art-director call is wired in ahead of
the local fallback but Pollinations' text API is currently 402-paywalled — the call
fails fast and self-heals if the free tier returns.

**2026-07-30 — Deployed-version fix** (follow-up to Florian's report: stuck at ~77%,
`dyn_platform` load error, green collider boxes). Two causes: the Pollinations proxy
only existed in the dev server (fixed with `vercel.json` rewrites — the free path now
works in production), and the failure-downgrade path in the deployed build re-fetched
broken URLs instead of falling back to built-in theme art (fixed; the scene also
double-checks its textures at boot). Failure now always ends in a playable game.
